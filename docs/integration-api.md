# API Мерчанта для Бітрікс24 та 1С

Версія 1 · базова адреса `https://hs-merchant.vercel.app/api/integration/v1`

Інтеграція стосується **лише замовлень**. Каталог віддається окремим
маршрутом, але тільки для того, щоб зіставити номенклатуру — товарами Мерчант
не керує ззовні.

---

## Як це працює загалом

```
   маркетплейс                Мерчант                  Бітрікс / 1С
   ───────────                ───────                  ────────────
   нове замовлення  ──────▶   приймає, рахує
                              комісію, суми
                                   │
                                   ├── вебхук order.created ──▶ створює угоду
                                   │
                              оператор узгоджує
                              склад, позначає оплату
                                   │
                                   ├── order.status_changed ──▶ в комплектацію
                                   │
                                                          склад збирає в 1С
                                   │                             │
                              перераховує суми  ◀── POST picking ─┘
                              й вагу накладної
                                   │
                                   ├── order.items_changed ───▶ актуальні суми
                                   │
                              ТТН, відправка
                                   └── order.updated ─────────▶ закриває угоду
```

Два канали одночасно, і це навмисно:

* **вебхуки** — зміна долітає за секунди;
* **опитування** `GET /orders?since=…` — підстраховка.

Втрачений вебхук не має губити зміну. Курсор рахується від часу оновлення
замовлення, а не від надісланих вебхуків, тож опитування наздожене будь-що.

---

## Автентифікація

Кожен запит несе ключ:

```
Authorization: Bearer mk_live_xxxxxxxxxxxxxxxxxxxxxxxx
```

Ключ видається один раз і зберігається в нас **лише хешем** — відновити його
неможливо, лише перевипустити.

### Права

| Право | Що дозволяє |
|---|---|
| `orders:read` | читати замовлення |
| `orders:write` | передавати комплектацію й нотатки |
| `orders:status` | змінювати статус |
| `products:read` | читати каталог для зіставлення номенклатури |

### Обмеження частоти

За замовчуванням **120 запитів за хвилину**. Перевищення — `429` із
заголовком `Retry-After: 60`.

Для опитування цього з запасом: 2000 замовлень на місяць — це одна сторінка
на хвилину.

---

## Номенклатура: як упізнати товар

Назва товару на маркетплейсі й назва в 1С — **різні тексти**. Зіставляти за
назвою не можна.

У кожному рядку замовлення приходить блок `nomenclature`:

```json
{
  "uid_1c": "fc81ddbe-6622-11f0-8681-d45d6408b3ce",
  "code_1c": "NF-00009045",
  "sku": "К0067",
  "catalog_name": "Шпондер свинний копчений"
}
```

* **`uid_1c`** — GUID номенклатури 1С. Основний ключ зіставлення.
* **`code_1c`** — код номенклатури (НФ-…). Запасний, читабельний для людини.
* **`sku`** — наш артикул.
* **`catalog_name`** — назва з нашого каталогу; `title` поруч — назва, яку
  бачив покупець на маркетплейсі. Вони відрізняються, і це нормально.

Обидва ідентифікатори 1С надходять із сайту та оновлюються щоденною
синхронізацією. Станом на запуск заповнені в усіх активних товарах.

## Читання замовлень

### `GET /orders`

| Параметр | Опис |
|---|---|
| `since` | ISO 8601. Усе, що змінилось **після** цієї мітки |
| `status` | точний статус, напр. `Узгоджено` |
| `platform` | `maudau` або `rozetka` |
| `limit` | до 200, за замовчуванням 50 |

```bash
curl -H "Authorization: Bearer $KEY" \
  "$BASE/orders?since=2026-10-12T08:00:00Z&limit=100"
```

```json
{
  "orders": [ { "...": "див. нижче" } ],
  "next_since": "2026-10-12T09:14:22.431Z",
  "count": 100
}
```

**Як гортати правильно:** збережіть `next_since` і передайте його наступним
запитом. Коли приходить `null` — нових змін немає, можна спати до наступного
циклу.

Не використовуйте номери сторінок: поки ви гортаєте, у Мерчанті тривають
зміни, і замовлення перестрибували б через межу сторінки.

### `GET /orders/{id}`

Приймає і наш UUID, і номер маркетплейсу — `MD-123456`, `RZ-789012`.

### Форма замовлення

```json
{
  "id": "6f2a…",
  "external_id": "MD-1234567",
  "platform": "maudau",
  "order_date": "2026-10-12",
  "status": "Узгоджено",
  "is_paid": true,
  "customer":  { "name": "Петренко Іван", "phone": "+380671234567" },
  "delivery":  { "address": null, "branch": "Відділення №12", "ttn": "20450912345678" },
  "money":     { "total": 1184.50, "commission": 142.14, "currency": "UAH" },
  "comments":  { "customer": "Подзвоніть перед виїздом", "operator": "Комірник: шпондер замінено" },
  "items": [
    {
      "id": "a71b…",
      "position": 1,
      "title": "Шпондер свинний копчений, 800 г",
      "nomenclature": {
        "uid_1c": "fc81ddbe-6622-11f0-8681-d45d6408b3ce",
        "code_1c": "NF-00009045",
        "sku": "К0067",
        "catalog_name": "Шпондер свинний копчений"
      },
      "unit": "кг",
      "unit_weight": 0.8,
      "price_per_unit": 359,
      "ordered_qty": 1.6,
      "actual_qty": 1.54,
      "removed": false,
      "line_total": 552.86
    }
  ],
  "updated_at": "2026-10-12T09:14:22.431Z"
}
```

**Про ціни.** `price_per_unit` — ціна **маркетплейсу**, не наша прайсова.
Покупець погодився на те, що побачив, і саме з цією сумою мають збігатись
комісія й оголошена цінність накладної. Наші ціни є в `GET /products` і для
розрахунків із покупцем не використовуються.

**Про кількості.** `ordered_qty` — скільки замовлено; `actual_qty` — скільки
зібрано фактично, `null` поки не комплектували. `line_total` рахується з
фактичної кількості, якщо вона є.

## Передавання комплектації

### `POST /orders/{id}/picking`

```json
{
  "lines": [
    { "uid_1c": "fc81ddbe-6622-11f0-8681-d45d6408b3ce", "actual_qty": 1.54 },
    { "code_1c": "NF-00009112", "actual_qty": 0, "removed": true }
  ],
  "note": "Шпондера не вистачило, зібрали менше"
}
```

Рядок шукається за `uid_1c`, далі `code_1c`, далі `sku`, далі `line_id`.
Досить одного.

```json
{
  "ok": true,
  "applied": 2,
  "unmatched": [],
  "totals": { "ordered": 1184.50, "corrected": 1102.30, "diff": -82.20 },
  "weight_kg": 2.34,
  "order": { "...": "замовлення цілком, уже перераховане" }
}
```

Мерчант **сам перераховує** суму, комісію та вагу накладної — тими самими
правилами, якими це робить оператор вручну. Присилати перераховані суми не
потрібно й не можна: два шляхи до одного результату не повинні рахувати
по-різному.

Позиції, яких не вдалося зіставити, повертаються в `unmatched` — запит при
цьому не відхиляється, решта застосовується. Перевіряйте це поле.

**Коли закрито.** Після `Узгоджено` склад замовлення замикається разом із
ТТН: накладна вже несе вагу й цінність. Спроба змінити дасть `409`.

### `POST /orders/{id}/notes`

```json
{ "text": "Клієнт просив подзвонити перед виїздом", "author": "Комірник Олег" }
```

Дописується до коментаря оператора, не замінює його. Автор потрапляє в сам
текст, а не лише в журнал: оператор читає коментар, а не історію змін.

### `PATCH /orders/{id}/status`

```json
{ "status": "Узгоджено" }
```

Правила Мерчанта діють так само, як для операторів:

* замовлення в доставці статус не змінює — `409`;
* неоплачене замовлення не поїде: `На доставці`, `Прибуло`, `Доставлено`
  вимагають позначеної передоплати — `409`;
* **скасування через API неможливе** — воно потребує причини й окремого шляху
  до маркетплейсу. Скасовують у Мерчанті.

## Вебхуки

Ми надсилаємо `POST` на вашу адресу:

| Подія | Коли |
|---|---|
| `order.created` | нове замовлення з маркетплейсу |
| `order.status_changed` | статус змінився з будь-якого боку |
| `order.items_changed` | змінився склад або комплектація |
| `order.note_added` | додано коментар |
| `order.canceled` | замовлення скасовано |
| `order.updated` | решта: ТТН, оплата, відправка |

```http
POST /your/endpoint
Content-Type: application/json
X-Merchant-Event: order.items_changed
X-Merchant-Delivery: 9b1c…
X-Merchant-Signature: 4f3a…
```

Тіло — `{ "event": "...", "sent_at": "...", "order": { … } }`, де `order`
має **ту саму форму**, що й у `GET /orders`.

### Перевірка підпису

```php
$expected = hash_hmac('sha256', file_get_contents('php://input'), $secret);
if (!hash_equals($expected, $_SERVER['HTTP_X_MERCHANT_SIGNATURE'])) {
    http_response_code(401);
    exit;
}
```

Підпис рахується від **сирого тіла**, до розбору JSON.

### Повтори

Відповідайте `2xx` якнайшвидше — обробляйте після відповіді. Якщо ми не
отримали `2xx`, спроби повторюються через 1 с, 1 хв, 5 хв, 30 хв, 2 год, далі
доставка позначається невдалою.

Одна подія може прийти двічі — мережа ненадійна в обидва боки. Орієнтуйтесь
на `X-Merchant-Delivery` або на `updated_at` замовлення.

---

## Повтори ваших запитів

Будь-який запис приймає заголовок:

```
Idempotency-Key: будь-який-унікальний-рядок
```

Повторний запит із тим самим ключем поверне **збережену відповідь**, не
виконуючи дію вдруге, і додасть `X-Idempotent-Replay: true`.

Використовуйте це завжди для `picking`: з'єднання рветься після того, як
робота вже зроблена, і без ключа комплектація застосувалась би двічі.

## Каталог

### `GET /products`

Для разового зіставлення довідників і подальшої звірки.

```json
{
  "uid_1c": "fc81ddbe-…", "code_1c": "NF-00009045", "sku": "К0067",
  "barcode": "4820…", "name": "Шпондер свинний копчений",
  "unit": "кг", "pack": "0.8", "price": 359, "stock": 12.4,
  "category": "М'ясні копченості", "merchant_id": "953800",
  "updated_at": "2026-10-11T03:02:11Z"
}
```

`price` тут — **наша сайтова ціна**, не маркетплейсова. `pack` — крок продажу
вагового товару.

## Коди відповідей

| Код | Що означає |
|---|---|
| `200` | добре |
| `400` | помилка у вашому запиті — текст у полі `error` |
| `401` | ключ відсутній або невідомий |
| `403` | ключу бракує права, або дія заборонена (скасування) |
| `404` | замовлення немає |
| `409` | дія суперечить стану: склад закрито, не оплачено, вже в доставці |
| `429` | перевищено частоту, чекайте `Retry-After` |
| `5xx` | наша проблема — повторіть із тим самим `Idempotency-Key` |

Помилка завжди має вигляд `{ "error": "текст українською" }`.

## Хто автор зміни

Усе, що приходить через API, лягає в журнал замовлення з іменем клієнта
інтеграції — наприклад «Бітрікс24 (інтеграція)». Оператор у Мерчанті бачить,
що склад змінив не він, і коли.

Це важливо, бо комплектацію можна правити **з обох боків**: 1С передає через
Бітрікс, оператор править у Мерчанті. Виграє остання зміна, а журнал показує,
чия вона була.
