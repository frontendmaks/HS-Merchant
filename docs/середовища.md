# Два середовища: продакшн і тест

## Що їх розрізняє

Одна змінна оточення:

```
MERCHANT_ENV=test
```

Її відсутність означає продакшн. Так зроблено навмисно: забути ввімкнути
тест безпечніше, ніж забути ввімкнути продакшн.

## Що саме робить тестовий режим

Мерчант працює звичайно — приймає замовлення, рахує зони й склади, бере
номери ящиків, веде журнал, — але **назовні не виходить нічого**:

| система | у тесті |
|---|---|
| Бітрікс | читання працює; угоди, стадії, позиції, контакти, чат — ні |
| Чат складу | бланк не йде |
| Trello | картку не правимо |
| Нова Пошта | довідники читаємо; накладну не створюємо й не видаляємо |
| MauDau | статус і ТТН на майданчик не їдуть |
| Rozetka | читання працює; запис — ні |
| Каталог сайту | товар не змінюємо |
| Google Таблиці | аркуш складу не правимо |
| Telegram | клієнтам не пишемо |
| Вебхуки інтеграцій | чужим системам не стукаємо |

Кожен затриманий виклик лишає в логах рядок:

```
[ТЕСТ] не вийшло назовні → Бітрікс: crm.deal.add {"fields":{...}}
```

Мовчазне гальмо було б гіршим за відсутнє: без цього рядка незрозуміло,
чому замовлення «пішло в Бітрікс», а його там немає.

### Чому гальмо, а не окремі ключі

Тестового Бітрікса в нас немає — як і тестових MauDau, Rozetka, Нової
Пошти. Якби тест ходив тими самими ключами, перша ж перевірка створила б
справжню угоду й надіслала справжній бланк, а склад пішов би збирати
вигадане замовлення.

Гальмо стоїть у найнижчих функціях — тих, якими ці системи викликаються з
усього коду. Обійти його, написавши новий виклик десь нагорі, не вийде.

### Чому дозволений перелік, а не заборонений

Для Бітрікса дозволено читання (`.get`, `.list`, `.fields`, `.search`),
заборонено решту. Перелік заборонених довелось би поповнювати щоразу, як
з'являється новий метод, і одного забутого рядка досить, щоб тест завів
справжню угоду. Забутий читальний метод такої ціни не має: він просто
впаде з виразною помилкою.

### Що відповідають загальмовані виклики

Не помилку, а правдоподібний успіх: вигаданий номер угоди на `.add`,
`true` на решту. Інакше тест перевіряв би лише першу половину ланцюжка —
заведення впало б, і все, що мало статись далі (номер ящика, бланк,
картка на дошці), не перевірилось би ніколи. Вигадані номери починаються
з 9 000 000: таких у Бітріксі немає й не буде.

## Як видно, що ти в тесті

Жовта смуга через увесь екран на кожній сторінці й «ТЕСТ ·» у назві
вкладки. Два вікна поруч виглядають однаково, а помилитись вікном означає
скасувати справжнє замовлення, думаючи, що воно вигадане.

## База даних

Код бере базу зі звичайних змінних — `NEXT_PUBLIC_SUPABASE_URL`,
`NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`. Щоб тест мав
свою базу, досить вказати в них інший проєкт Supabase.

**Поки окремої бази немає.** Другий проєкт Supabase коштує $10 на місяць,
і це рішення власника, а не розробника. Доти тестове середовище працює з
тією самою базою, що й продакшн: зовнішні системи захищені гальмом, а от
самі замовлення тест і продакшн ділять. Для перевірки інтерфейсу й
розрахунків цього досить; для перевірки того, що створює й скасовує
замовлення, — ні.

Коли база з'явиться, схему переносить `supabase db push` (міграції лежать
у `supabase/migrations`).

## Як запустити локально

```bash
MERCHANT_ENV=test npm run dev
```

## Як розгорнути тест окремо

1. У Vercel створити оточення (окремий проєкт або гілку `staging`).
2. Додати змінну `MERCHANT_ENV=test`.
3. Якщо є окрема база — підмінити три змінні Supabase.
4. `NEXT_PUBLIC_APP_URL` має вказувати на адресу тесту, інакше посилання
   на бланки вестимуть у продакшн.

Розклади (`vercel.json`) у тесті працюють і це правильно: саме їх і треба
перевіряти, а все небезпечне з них однаково загальмоване.
