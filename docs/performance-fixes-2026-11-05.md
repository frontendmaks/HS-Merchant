# Виправлення HS Merchant — 5 листопада 2026

## Розгорнуто

Production: https://hs-merchant.vercel.app

Аварійний пакет: `hs-merchant-j9bcxouhp-maksyms-projects-f848383a.vercel.app`.
Основний пакет: `hs-merchant-28heectpc-maksyms-projects-f848383a.vercel.app`.

- Middleware перенесено у Node Proxy; login відкривається без перевірки старої сесії. Перевірка приватних сторінок лишається, її очікування обмежено. Серверні функції працюють у `fra1`, що підтверджено Vercel inspect.
- Вхід, сесії й зовнішні HTTP-виклики мають обмежене очікування. Роль та ім'я користувача читаються через спільну request-scoped функцію; browser client єдиний. Асинхронну роботу винесено з callback блокування Supabase Auth.
- Важкий view останніх цін читає готову приватну materialized view; оновлення кожні 5 хвилин. Каталог для ручного замовлення кешується між запитами й має single-flight заповнення.
- Каталог товарів завантажується по 50, фільтри/сортування рахуються у SQL, опис — на відкриття картки. Збережені всі попередні фільтри. Маркетплейси мають пагінацію й вибір лише потрібних полів; raw payload замінено витягнутими timestamp. На вкладці «Сайт» рендериться до 50 рядків із підсумками всього зрізу.
- Події оновлення списку об'єднуються з обмеженою затримкою, пошук має debounce. Непотрібні polling-запити навігації у фоні зупинено. Два адаптивні дзвіночки більше не запускають одночасно дві петлі. Read-only polling ділиться між компонентами/вкладками одного користувача через BroadcastChannel/Web Locks; desktop notifications збережено.
- Лічильники виконують один SQL RPC із персональним ключем кешу замість чотирьох COUNT і регулярного getUser.
- Зміна статусу захищена DB lease, повтор уже застосованого статусу є no-op. Платформа та зовнішній ID беруться з бази. Статус локально записується після підтвердження зовнішньої системи; запис, журнал і durable outbox — одна транзакція, з перевіркою версії updated_at. На маршрут додано перевірку write-role.
- Бланк складу має атомарну унікальну claim-запис перед відправкою; синхронізація та оператор не можуть надіслати його паралельно. Підтверджений send відновлюється з ledger, якщо процес не встиг проставити chat_sent_at. Невизначений результат після timeout позначається в замовленні та не надсилається автоматично вдруге: перед повторенням треба звірити чат складу. Абсолютну exactly-once доставку через сторонній API без idempotency key гарантувати неможливо.
- Побічні дії статусу обробляються після відповіді з durable outbox; перервані jobs підбирає чинний cron webhooks. Зовнішні webhook-події мають ключ дедуплікації, delivery-прохід — lease. Повторні повідомлення клієнту додатково захищені lease та перевіркою журналу.
- Події Bitrix підтверджуються після durable enqueue; повтори однієї угоди об'єднуються. Черга зберігає подію, що прийшла під час обробки старішої. Sweeps, autopilots і створення угоди захищені lease. Статуси sweep і ручної дії мають спільний per-order lock та optimistic update. Незмінені дані Bitrix пропускаються за fingerprint.
- Аналітика кешує готові агрегати на 60 с, обмежує одночасні запити журналу, не читає presence ticks для передачі в JS. Online minutes рахуються в SQL за попереднім правилом 7 хвилин і змінами у Europe/Kyiv. Карти завантажуються ліниво. Дані для ролі analyst мають окремий ключ кешу, операторська статистика їй не передається.

## Перевірено

- Production-збірка Next.js пройшла локально й у Vercel.
- 77 автоматичних тестів; нові сценарії перевіряють приватні сторінки/збої Auth, паралельні зміни статусу, відмову зовнішньої системи, повтор статусу, race двох відправок бланка та невизначений timeout, повноту пагінації.
- Жива база: read останніх цін `EXPLAIN ANALYZE` після зміни — 5,411 мс, попередній одиничний замір — 45 486,639 мс. Це SQL execution, а не час відкриття екрана.
- Перша сторінка каталогу — 50 із 2594; компактний JSON у перевірці ~32 КБ, попередня оцінка повного набору ~1,97 MiB до стиснення. Дві послідовні сторінки — 100 різних ID; counts active/in-stock збігаються з незалежними запитами до таблиці.
- SQL presence порівняно з попереднім JS `onlineMinutes` на 13 967 реальних записах: 0 розбіжностей, результат 2 рядки за користувачами.
- DB tests у транзакції перевірили lease ownership, неможливість другої claim бланка, стан завершення, дедуплікацію події Bitrix, service-role доступ. Усі тестові записи відкотились.
- Нові RPC недоступні anon/authenticated; приватні таблиці мають RLS без клієнтських policies, доступ лише service_role. Security advisors не показали нових ERROR/WARN для доданих об'єктів; інформаційне «RLS без policy» тут відповідає навмисній забороні клієнтського доступу.
- Після аварійного deploy login HTTP 200 за 0,345 с; у наявній авторизованій Chrome-сесії відкрились «Замовлення → Сайт» та каталог.
- Після першого пакета у живій черзі були 2 завершені side-effect jobs і 2 підтверджені відправки бланків, без pending/uncertain у цьому знімку. Це не довготривала статистика надійності.

## Експлуатаційні межі

Готові історичні ціни можуть відставати до 5 хвилин; звіт — до 60 с; навігаційні лічильники — короткий TTL і період опитування. Поточні ціни товарів та підтвердження статусів не підміняються історичним кешем.

Jobs мають обмеження спроб і час lease; невизначену доставку бланка потрібно перевіряти через chat_error/чат складу. HTTP-повтори webhook використовують той самий X-Merchant-Delivery, який приймач має дедуплікувати.

Тарифи, розмір compute й чужі старі RLS-політики не змінювались без підтвердженої потреби. Після роботи потрібне звичайне спостереження за p95 і ресурсами у пікові години: наявні заміри не доводять конкретного p95 для всіх робочих сценаріїв. Уже створені раніше дублікати замовлень/бланків не видалялись.
