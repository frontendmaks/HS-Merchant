# Повторний збій входу — 5 листопада 2026

## Спостереження

Після повідомлення про `signal timed out` перевірено поточну базу, Auth, Vercel і панель Supabase.

- На 14:51 UTC черга Bitrix порожня, масової активності чи lock waits у базі не було; останні синхронізації зазвичай завершувалися за секунди.
- Логи Auth містили успішні входи до приблизно 14:48 UTC. Наступні прямі запити до публічного JWKS Auth почали зависати без відповіді, тоді як `/rest/v1/` повертав очікуваний 401 за ~0,11 с.
- DNS і TLS до Supabase успішні; зависання відбувається після надсилання HTTP-запиту Auth. Та сама проблема відтворена з локальної перевірки й сервера Vercel.
- Панель Supabase показала `Unhealthy`, compute `Nano` та попередження про майже вичерпаний Disk IO Budget із baseline 5 MB/s. Це підтверджує проблему стану сервісу; точну причину зупинки Auth лише за цими даними не встановлено.
- Попередній короткий timeout у Proxy міг переспрямовувати чинну сесію на login під час тимчасової помилки. Це окремий недолік обробки відмов, виправлений у цьому пакеті.

## Розгорнуті зміни застосунку

Production deployment: `hs-merchant-cvbgx1aqu-maksyms-projects-f848383a.vercel.app`.

- Browser Auth працює через same-origin `/api/auth/bridge/*` із фіксованим upstream Supabase, allowlist маршрутів/методів, обмеженням розміру, перевіркою Origin і `no-store`. Використовується лише публічний ключ; service-role не бере участі у вході.
- У разі upstream timeout bridge повертає retryable 503, а не невизначену помилку, що могла спричинити втрату сесії.
- Чинний access token перевіряється `getClaims(jwt)` без примусового refresh при читанні сторінок; декодування cookie саме по собі не використовується для авторизації.
- Лише прострочений токен запускає refresh у Proxy. Refresh не переривається Promise.race, яка могла загубити Set-Cookie після ротації токена.
- Тимчасова помилка Auth дає захищену сторінку 503 із повтором, а не redirect на login; недійсний токен і відсутня сесія не допускаються до приватних даних.
- Login має зрозуміле повідомлення й після успіху відкриває новий документ із актуальними cookies.
- Додано спільний DB lease для обробників Bitrix events, щоб burst різних угод не створював необмежену кількість workers.

## Перевірки та стан відновлення

- 86 тестів і production-збірка пройшли, включно з новими сценаріями refresh, збереження cookie при мережевій помилці, прямої перевірки JWT, обмежень bridge та chunked cookies.
- Живий bridge підтвердив поточну недоступність Auth: 503 після 20 секунд; це не підтвердження успішного входу.
- Спроба натиснути `Restart project` у панелі Supabase була заблокована автоматичною перевіркою, яка вимагає окремого дозволу користувача на кілька хвилин недоступності production. Дозвіл запитано; до підтвердження перезапуск не виконується.
- Compute, оплата, паролі та ключі не змінювалися.
